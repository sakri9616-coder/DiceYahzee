## 2. シミュレーションが露呈させた問題（再開時の起点）

同一シード3000試合の初期結果：

| 組み合わせ | 結果 |
| --- | --- |
| 攻撃型 vs 守護型 | 346–152（**攻撃型 69%**）＝ 攻撃偏重が支配的 |
| 攻撃型 vs 均衡型 | 295–201（59%） |
| 守護型 vs 守護型 | 平均12ラウンド（上限到達100%）、引き分け16.8%、与ダメージ合計 約2.5/試合 |
| 均衡型 vs 均衡型 | 平均4ラウンド、引き分け0.6%（健全） |

構造分析：自HP差分 `net = max(0, S − To) − max(0, S − Tm)`（`S = 自攻撃 + 相手攻撃`）。
つまり**割り当ての正解は「自分の合計が高そうなら攻撃、低そうなら守護」**であり、
初期実装は（1）攻撃型だけ振り直し閾値が異なり合計の期待値が高かった、
（2）合計の良し悪しを見ていない固定期待値だった、（3）守護型は常に守護へ寄るため非対称な交換になっていた、という3つの欠陥があった。

### 2.1 独立批評（改善前・今回取得）

**game-critic（詳細版）** — 要旨：

1. 攻撃偏重は`max(0, attack − guard)`の線形貫通そのものが助長しており、構造的に支配的。
2. 防御が合理的に選ばれる状況は現状ほぼ存在しない（固定の`TypicalAttack`しか見ていないため）。
3. 守護型の判断は根本的に欠陥（閾値3で合計が伸びない＋固定期待値で自分が厚くした守護の効果を評価できない）。
4. 防御同士の膠着は**ルール構造に由来する**（貫通不能の壁が高い）。
5. 提案：**案1（NPCアルゴリズム修正）を最優先**、膠着には**案4（貫通失敗時の押し勝ちダメージ）を並行導入**。
   案2（ペアリング方式）は認知負荷が高く却下、案3（シールド持ち越し）はテンポを落とすので却下。

**code-reviewer（短文・技術検証）** — 要旨：

1. `MatchEngine`の同時適用・HP判定・時間切れ判定：**問題なし**。
2. `NpcBrain`の期待値計算：`TypicalGuard = 4.2`／`TypicalAttack = 13.3` というハードコード値の根拠が弱い（severity: low）。
3. **シミュレーション集計にバグあり**：`AverageRounds = Rounds / (Wins + Draws)` としており、敗戦分の分母が抜ける。
   → 平均ラウンド数の数字を過大評価していた（12ラウンド上限の試合が「22.47」と読める原因）。

### 2.2 採否

| 対応 | 採否 |
| --- | --- |
| 集計バグ修正（分母＝参加試合数、ラウンド上限到達率・引き分け種別の追加） | **ACCEPT**（測定の前提なので） |
| 案1：振り直し閾値を全陣営一律4に統一 | **ACCEPT** |
| 案1：割り当て判断を合計ベースの期待値モデルに置換 | **ACCEPT** |
| 案1：HP差によるリスク調整を全陣営で対称に | **ACCEPT** |
| 案4：貫通不能時の押し勝ちダメージ | **ACCEPT**（案1だけでは膠着が残ると予測し、実測でも残った） |
| 案2（攻守のペアリング方式） | **DEFER** — 構造的には正しいが、画面説明・UI・既存テストの書き換えが大きく、先に最小変更で効果を測る方針 |
| 案3（ダメージ上限＋シールド持ち越し） | **REJECT** — テンポを悪化させる |

### 3.2 ユーザーが挙げた5点への回答

1. **攻撃偏重が支配的最適か** — 初期は69%で支配的だったが、閾値統一と合計ベース判断で0.53に収束。
2. **防御が合理的に選ばれる状況は存在するか** — 手が悪いときは守護へ寄せる。守護型の攻撃2個選択は58%、均衡型は攻撃数の分布が最も分散（最多使用シェア0.48）。

5. **試合時間・テンポの悪化** — 全組み合わせで平均ラウンドは基準以下（攻撃同士は1.67→2.04と微増だが、最短カテゴリは依然2ラウンド）。全体平均は約4.7ラウンド。

## 4. ルール最終形

- 5d6、HP20、振り直し最大2回、攻守分割（各1個以上）、同時公開
- ダメージ = `max(0, 攻撃合計 − 守護合計)`
- **貫通不能時は合計の高い側が押し勝ち3ダメージ**
- ラウンド上限10
- 同時撃破：与ダメージ合計 → 最終ラウンドのダメージ → 引き分け
- 時間切れ：残りHP → 与ダメージ合計 → 引き分け

> **注意**: 上記は v1 の最終形。v2 以降は §5 を参照。

## 5. 再設計 v2（プレイテスト指摘 + 独立批評3系統を受けて）

### 5.1 なぜ捨てたか

人間のプレイテストで4点の不満が届き、それに独立批評3系統が一致した（`docs/DESIGN_REVIEW_V2.md` §2）。

決定的だったのは **攻守分割が1本のスカラーに潰れる**という構造的事実である。
攻撃合計 `S`・自分の守護 `Tm`・相手の守護 `To` とすると、
`net = max(0, S − To) − max(0, S − Tm)` で、**分割は `S = a + A` の取り方1つにしかならない**。
実装上「分割の自由度」が存在しても、効いてしまうのは1変数だけ。
標準ヤッツィーや Dice Throne と比べて、現行の核に勝ち目は無いという結論に至った。

### 5.2 新しい中心

> **5ダイスで「陣形」を組み、その陣形を攻撃に組み込めるか、守りに裂くかを選ぶ。**

- **陣形**: スリーカインド（同じ目3個）= +5、ストレート（**4連続**）= +5。攻撃側に構成のダイスを**全部**入れると成立。
- **加算は貫通判定の外側**：貫通できなくても陣形は必ず効く。
- **操作統合**: モードを廃止し、各ダイスを 3 状態（攻 / 守 / 振）の巡回1クリックに。
  `振り直す` は「振」のダイスだけをやり直し、割り当ては保持される（`_sideBeforeReroll`）。
- `GameConfig.FormationsEnabled` のデフォルトは false のまま（既存41件は旧ゲームを測る）、
  出荷時は `GameConfig.ApplyShippedPatternLayer()` で有効化する。

### 5.3 計測で判明したこと（設計の外側の欠陥）

1. **陣形は「役」になる前と後で別の問題を抱えていた。** 初版（対あり・3連続階段・HP20）では
   成立率 0.73・ボーナス比率 0.39 で、役ではなく毎回もらえる税だった。試合長は 4.65 → 2.37 ラウンドに半減。
2. **検証側の欠陥**: スイープ初回で先手勝率 0.719 が出た。既存のミラー検証は「同じ型どうしの勝率」
   だけを見ているため**席順の偏りを検出できない**。原因は**両席の判断ロジックが別物**だったこと
   （NPC は `NpcBrain.TakeTurn`、プレイヤー席は素の閾値ポリシー）で、**陣形オフのときだけ一致していた**。
   つまり v1 の均衡は偶然の一致だった。
   → リロール方針を `NpcBrain.PlanReroll` に共有し、**席バイアス検証（先手勝率 0.45–0.55）を追加**。
   以後、3000試合の集計先手勝率は 0.4840（v1 は 0.4817）。いずれも許容帯 0.45〜0.55 の内側。
3. **教訓**: 勝率が均衡していたことは、両対戦相手が同じルールで動いている証拠にならない。

### 5.5 再設計後に実装したもの

- **単一画面3状態操作**（攻 / 守 / 振り直しの巡回）。モード自体を廃止した。
- **`_sideBeforeReroll`**: 振り直しても割り当てを保持し、再割り当て入力を0にした。
- **公開バナーの内訳表示**（攻 + 陣形 − 守 = 実ダメージ、両側）。
- **HP リビール・トゥイーン**: 0.45秒の ease-out で実値に着地。入力をブロックせず、
  必ずエンジンの実値で終わる（スキップ可）。`RevealMotionTests` が3つの約束を検証。
- **陣形成立スティング** `formation.mp3`（StepAudio 生成）。
- **操作ログの複数試合化**: 各ポリシー5試合・計20試合（`runsPerPolicy: 5`）。
  1試合では試合長の偶然が入力数にそのまま出てしまうため。

（`攻撃型 vs 守護型` が 0.5340/0.4660 → 0.6606/0.3394）。
公平性の欠陥ではないが、「どのNPCと戦うか」が勝敗をかなり左右する。

## 6. 再設計 v3（役宣告型）と演出（2026-10-10）

### 6.1 ユーザーの指摘とヤッツィーの分析

ユーザーから4点の不満が届いた（v2 の UI に対して）。

1. クリック数が多く、流れが悪い
2. 攻守の割り当てと振り直しが往復し、緊張が持たない
3. ヤッツィーの「役」が無いことが残念
4. 何が起きたか分かりにくい

さらに明確な指示があった（逐語）：

> ・操作手順の煩雑さが解消されていません。むしろ、クリック回数による切り替えは操作数を増やっています。
> ・役の概念を導入する方向で検討してください。
> ・ヤッツィーの要素から何が駆け引きを生み出しているのかを分析してください。現時点では、ヤッツィーから借用できているルールは5個のダイスを振る、と言う部分だけです。

この指摘は正しかった。公式ルール（Hasbro、`https://www.hasbro.com/common/instruct/Yahtzee_%282003%29.pdf`）を
読み直して、ヤッツィーが駆け引きを生み出している要素を7つに分解した。

| # | ヤッツィーの要素 | ARCANE DUEL v2 が持っていたか |
| --- | --- | --- |
| E1 | カテゴリーごとに**13スロットが1つずつ**あり、使うと二度と使えない（枯渇） | なし |
| E2 | 「上位○個の合算」と「役単独」で**配分先が固定か合算か**が分かれる | なし |
| E3 | 63点以上の**二次目標ボーナス** | なし |
| E4 | 同じ1手札を**別の配分先に割り当てる** | あり（ただし1本のスカラーに潰れる） |
| E5 | どのダイスを**保持して振り直す**か＝目標を絞る判断 | あり |
| E6 | 逃げ道（チャンス）が**常に1つだけ** | なし |
| E7 | 後半になるほど**高役の配分が積み上がる** | なし |

**v2 が実際に持っていたのは E4・E5 だけで、しかも E4 は §5.1 の恒等式により
「合計の良し悪し」1変数に潰れていた。** ユーザーの言うとおりだった。

### 6.2 v3 の決定：役が全部を決める（A1）

独立批評2系統（`game-critic` / `code-reviewer`）が**同じ結論**に到達した。

> **A1：役が攻守の割り当てを全部決める。手動の攻守分割は廃止する。**

採用した。役表は `GAME_DESIGN.md` §2.3 に置いた。
判断の根拠は次の3点。

1. **操作数が減る**。分割の操作自体が消えるので、v2 の「往復」が発生源として無効になる。
2. **E4 が生き残る**。役が「何個前へ出すか」を決めるので、
   「スリーカインドを全部前へ出すか、裂いて守るか」が実質的な選択として残る。
3. **役が得点になる**（ユーザーの3点目の指摘）。合算ではなく固定攻撃という
   **ヤッツィーの「役単独」の価値**をそのまま持ち込める。

### 6.3 E1（役ごとに1試合1回限定スロット）は今回採らない（B1）

独立批評2系統ともに**今回の改修では導入しない**と勧めた。
導入を保留する条件として **「いずれかの役が全宣言の50%以上を占める」** を先に決めた
（判定は `Assets/Tests/EditMode/YakuAppealTests.cs` が機械的に行う）。

計測結果、**最も支配的な役は対の24.18%**で、条件には遠く及ばない
（`logs/yaku-appeal-report.json`）。**E1 はまだ借りていない。**

### 6.4 計測が暴いた構造的な問題：守護が大半を占める

役表を入れた直後の全7776手 × 3アーキタイプ × 3体力状態 = 69,984宣言の計測で、
**守護（何も前へ出さない）が全宣言の 78.11%** を占めていた
（`logs/yaku-appeal-report-baseline.json`）。
さらに試合側でも **3000試合の72.40%が10ラウンド満了まで進み、
1試合の総与ダメージはHP32に対して22.68** にとどまった
（`logs/simulation-report-yaku-baseline.json`）。

原因は恒等式にあった。出目の合算でできている役では `攻 + 守 = 手の合計` なので、

```
net = (攻 − 相手の守り) − (相手の攻 − 守)
    = 手の合計 − 相手の手の合計        （クランプの外側）
```

となり、**割り方で損益は変わらない**。
守護が例外なのは `max(0, 相手の攻 − 守)` を**強制的に0にできる**からである。
つまり「攻める正当性」は実質的に**自分の手が相手の想定手より良いか**だけに懸かっている。

`NpcBrain` はその判断に `TypicalOpponentTotal`（相手の手の合計）と
`TypicalOpponentAttack`（相手の攻撃）を使っている。
初期値は **23 / 14** という手打ちの推測値で、**両者の和が23になる一方、
このNPC自身の振り直し方針が作る手の平均は約21**だった。
相手が実際より強いと見積もられた結果、ほぼ全ての手が「相手より低い」と判定され、
**守護が合理的な正解になった**。勝率が均衡していても、
試合のほとんどが「何もしない」で進んでいた。

### 6.5 修正：相手の想定を推測ではなく測定にした

`Assets/Tests/EditMode/TypicalOpponentTests.cs` を追加し、
**このNPC自身が実際に振る手を54,000ターン分測定**して定数と突き合わせるようにした。

| 項目 | 測定値 | 修正前 | 修正後 |
| --- | --- | --- | --- |
| 相手の手の合計 | 20.8497 | 23 | **21** |
| 相手の攻撃 | 11.2035 | 14 | **11** |
| 相手の守り | 9.6462 | 9 | **10** |

（一次ファイル `logs/typical-opponent-report{,-baseline,-fixed}.json`）

計測結果：

**批評役の提案を採用しなかった点（正直な記録）**:
`game-critic` への相談では「守護にも攻撃1を与える」（`Add(Guard, 0, -1)` → `Add(Guard, 0, 1)`）が
推奨された。しかし `gain = max(0, 1 − 相手の守り)` は相手の守りが5以上である限り**0のまま**で、
**NPCの判断は1ミリも変わらない**。提案は棄却した。
採ったのは「相手の想定を実測値に合わせる」ことで、これは批評が挙げたレバーのいずれでもない。
批評はレバーA/B（想定値の変更・攻撃値の変更）を「守護偏重を助長する」と退けていたが、

**批評の結論と、その結論の根拠になっている数値を分けて検証したことになる。**

### 6.9 画面批評（2026-10-10 続き）

**出発点はユーザーからの指摘だった**：「画面批評を行っていないのではないですか？
もう一度、自分が活用できるものをすべて生かせているのか考えてください」
「既存の『評価されているゲーム』の画面と比較することは、大前提です」。

それまでの画面検証は**座標と文字列だけ**を読んでいた。
座標が正しく、ラベルが正しく、重なっていない — そのすべてが成立したまま
**形が正しく壊れた画面**は作れてしまう。実際にそうだった。

#### (a) 比較の相手と、見たものの差

比較対象は Yahtzee With Buddies の公式画像（`logs/ref-ywb-1..4.png`）。
差が出ている点は次の4つに整理した。

| 観点 | 基準 | 当初の本作 | 手当て |
| --- | --- | --- | --- |
| ダイスの形 | 白い**角丸**の立方体、影がある | **正円** | 九スライスをやめ、寸法一致スプライトへ |
| 役の名称 | ストレート／ヤッツィーなど**既知の語** | 小階段・三つ・五つ | 画面表示名をヤッツィー標準へ |
| 焦点 | 巨大で単一の CTA | 平らで均質な面 | 影・ビネット・金の一次ボタン |
| アスペクト | – | 4:3 で端から切断 | `CanvasScaler.Expand` |

#### (b) 撮る手段を作った（判断：検証側を先に足す）

批評は一回で終わる消費ではなく、**修正のたびにやり直せる**必要がある。
そこで PlayMode の実画面をカメラ → `RenderTexture` → PNG に保存する
`ScreenCaptureTests` を作り、批評を「見た感想」ではなく**再現可能な手順**にした。

1. 写真を基準画像と突き合わせる
2. 疑わしい箇所をスキャンラインに分解して記号列にし、形を**座標で**読む
3. 原因が分かったら、その形そのものを検証するテストを書く

`logs/screens.html` は整形表示用で、**図形を四角く描くため形の判定には使わない**。

#### (c) 写真が見つけた欠陥（3件）

1. **ダイスが正円・ボタンが楕円** — `Image.Type.Sliced` が border を
   *載せ先の矩形に比例*させて算出するため、64px/border16 のスプライトは
   載せ先の半分の角しか作れない。250単位のボタンの角半径は125で、これは楕円である。
   切り分けの単体撮影 `logs/unity-probe.png`（320×120が完全な楕円で写った）で確定させ、
   **ウィジェット寸法そのもののスプライト＋`Image.Type.Simple`** に変更した。
   対が守る検証は `SpriteSkinTests`（形状・アスペクト・キャッシュ）と
   `DiceShapeTests`（実画面のダイスが掴むスプライトが矩形と1対1）。
2. **4:3 で `ルール` ボタンが画面外** — `matchWidthOrHeight = 1f` が原因。
   `ScreenMatchMode.Expand` に変え、余白をレターボックス側へ回した。
3. **攻/守バッジが輪郭に食い込む** — `-0.4` → `-0.34`。
   「ダイスが傷ついている」ように見えた。

#### (d) ユーザーが名指しした2点

**① 役名を既存ヤッツィーに合わせる**
> 「役は『ストレート』『ヤッツィー』『フラッシュ』など、既存ヤッツィーの名称を取り入れるべきです。
> 安易な独自用語はユーザーを混乱させます。」

表示名を `Yaku.DisplayName` で一括変更した（小階段→小ストレート、大階段→大ストレート、
五つ→ヤッツィー、対→ペア、三つ→スリーカインド、チャンスは改称不要）。
陣形側の表示名（`Formation.DisplayName`）も既にストレート／スリーカインド／ペアで揃っていた。
**守護だけはヤッツィーの13種目に相当が無い**（全種が「前へ出す」前提で、
「全部を守りに回す」分類が存在しない）ため、ここだけは独自名称のまま据え置いた。
この例外は `GAME_DESIGN.md` §2.3 に明記している。
出典は Hasbro の公式ルール PDF。

**② 振り直しの表記と実動作の矛盾**
> 「画面の表記は『振りなおす』で、振りなおしたいダイスを選択させるUIなのにも関わらず、
> 実動作は『選択したダイス以外を振りなおす』となっています。重大な矛盾です。」

`StartThrow` に `kept`（保持した側）を渡していたのが原因で、
**選択したダイスが動く**ように直した。
表示と実動作の対は、プレイヤーが触る前に一度も確かめられていなかった種類の欠陥であり、
`Reroll_ThrowsExactlyTheDiceThePlayerMarked` が再発を防ぐ。

#### (e) 却下したもの

- **ネオン調・高彩度への寄せ方**（基準画像は暖色で飽和している）：
  本作の世界観は魔術決闘であり、暗闇に金という配色で通すことにした。
  彩度を基準へ合わせるのは比較に見合っていない。
- **ダイスの立体表現（ベベル・法線）**：コード生成のみの方針を守るため画像を使わず、
  影とリングで物体らしさを出す範囲にとどめた。
- **操作を待たせる演出の追加**：暗い手法（意図的な待ち時間）に該当しうるため対象外。

## 7. 予告・魔力・回復・三連決闘（0.4.0 / 2026-10-11）

ユーザーの完成基準は「Steamセールスランキングで一位を取れるレベルのクオリティ」。
実行版や配布の整備に重点を置く解釈を修正し、UI/UX、ゲームデザイン、ビジュアルの改善へ進んだ。
AI生成画像は禁止。Kenney、Lorc、Poly Haven、Aoboshi Oneのフリー素材を採用した。

旧仕様の課題は、相手の行動を知らずに期待値を選ぶ構造、通常役の差の小ささ、周回の動機の弱さ。
NPCの行動をプレイヤーの最初の投骰前に固定して予告し、ダメージ比較を操作中に見せる。
未使用の振り直しを魔力へ変え、役に1ラウンドの回復を加えた。
ペアは守り＋2、スリーカインドは攻撃＋3を双方に適用し、チャンスとの差を作った。

三連決闘は初戦前と勝利後の祝福選択で組合せを作り、体力を持ち越す。
初期調整（相手HP28/36/44、回復12）では簡易方針の制覇率が25/300（8.3%）と低かった。
相手HP28/34/40、回復16と役補正を適用後は60/300（20%）。
スリーカインド使用は44/3460（約1.3%）から337/3321（約10.1%）へ変化。
自動方針の測定を人間の楽しさや、最適方針の証明として扱わない。

7枠の役を固定し、予告→ダメージ→ダイス→役→操作の順で表示する。
革の卓、紋章と金の枠を統一し、実際のダメージに対応する攻撃・守りの演出を加えた。
連戦の祝福は対戦中にも確認できる。強化ボタンとHPの重なりは描画画像から見つけて修正。
三連決闘の通し操作では、同時撃破による勝利後もHPを0に補正してから16回復するケースを確認した。
旧設計と実測値は当時の履歴として保持し、現行仕様はGAME_DESIGN.md、検証はTEST_REPORT.md §12を参照する。

## 8. 振り直しと使い切りの役（0.5.0 / 2026-10-11）

ユーザーから、振り直し演出と役の採用は肯定された一方、常設の役表、成立通知の不足、
大役のノーガード、保守プレイの優位、高い目とチャンスへの偏り、魔力と独自用語による情報追加を指摘された。
今回の判断は「既存のシステムをまず疑う」「画面と操作をシンプルに」「1ターン約3判断」を優先した。

魔力、守護、攻守分割、合計押し勝ちと祝福を通常対戦から撤去。
役は一戦1回、チャンスも一戦1回とし、固定点の役同士を比較して差だけがHPに通る構造に変更。
ペア・ツーペア・3/4/5つの同目・フルハウス・2種のストレート・チャンスの9欄に対して6ターン。
低い目も固定点の役の材料になり、大役の成立はダメージを与えることと被害の軽減を兼ねる。

Hasbro公式ルールの最大3投・保持・得点欄1回制・チャンスの1回制・失敗時0点を分析した。
上段の6種類は本作に移植していない。9役の固定点と差分HPは本作の変更で、公式採点ではない。
参照: https://www.hasbro.com/common/documents/dad2af551c4311ddbd0b0800200c9a66/8302F43150569047F57EB8D746BA9D86.pdf

独立した252出目状態のモデルでは、6ターン先の欄消費まで考慮する方針と、そのターンの期待点だけを
最大化する方針の差は約0.9%だった。長期の温存戦略の深さを過大評価せず、保持と振り直しの判断を中心にする。
差分HPはKO以外では累積得点差に等しいため、予告が毎ターンの最適な期待点方針を大きく変えるとも主張しない。

NPCの当初の1手先推定は残り1回と2回を区別しなかった。実例 [1,1,1,5,5] は、残り1回なら32点で止める一方、
残り2回なら1を3個残して振る期待値が約35.12点になる。252出目・462保持集合・4368重み付き遷移で
残り1/2回を別に評価する完全列挙へ変更し、回帰テストで保持の違いを確認した。未来の出目は参照しない。

通常画面は5ダイスと現在の役1個へ集約。別の役の記録は任意の得点欄で、合法な0点選択も隠さない。
すべてのダイスが着地してから、使用可能な成立役のうち最も強い形を音・短い拡大・該当ダイスのまとまりで通知。
振り直し中の新結果の先出しを防ぎ、保持ダイスを静止させ、次ターンの開始も投擲演出に揃えた。
固定出目の練習は本番から分離。世界観用語で飾らず、具体的な操作と既存の役名で説明する。

正式なUnity検証による900試合（3方針×3NPC×100シード）では、役を狙う方針130勝、
高い目を残す方針29勝、相手の点数へ届いたら早く止める方針92勝。
これは3つの自動方針の比較であり、最適戦略や人間の楽しさの証明ではない。
詳細と通し操作の結果はTEST_REPORT.md §13を参照。旧仕様は比較用スナップショットに保持。

## 9. 出目・役の変化・直接操作・KOまでの対戦（0.6.0 / 2026-10-11）

ユーザー指定により、現行タイトルは「DiceYahzee」とする。綴りもこの指定に従う。
0.5.0で使っていた「ダイス対決（Dice Duel）」は当時の名称として履歴に保持する。

### 9.1 人間のプレイ評価を起点にする

0.5.0に対して、役の強さが変わったことを演出で認識したい、役を常に選べるようにしたい、
右クリックで振り直したい、ダイスを上へ弾いて確定したい、という要求を受けた。
敵が本当に予告の役を揃えたのか視覚的に信頼できない、役への依存が強すぎる、
敵を倒し切らずに終わるため未消化感がある、という問題も設計の対象とした。
さらに、1回だけ出目を保存し、その際は敵の攻撃を無防備に受ける選択が求められた。
追加要求として、使う役の一覧を右側へ置き、ホイールで切り替える操作を採用した。
ターン開始時は最も高得点の未使用役を提案し、プレイヤーが自分で選んだ役は振り直し後も維持する。役を狙う入力を自動提案が上書きしないための調整で、実際に揃った役の成立通知は別に維持する。

以前の「現在の役1つに情報を絞る」を固定した正解とはしない。今回の操作上の需要に応じて
右の9役を常設し、使う役を選ぶための画面遷移をなくす。複雑さは別画面の数ではなく、
実際に狙いを変えられるか、目と役と被害を結び付けて読めるかで評価する。

### 9.2 役だけが結果を決める構造を改める

固定得点だけでは、役が変わらない振り直しや揃わない手が結果に寄与しにくい。
得点を5個の合計＋選択役の成立ボーナスへ変更した。
ボーナスは順にペア4、ツーペア8、スリーカインド12、フルハウス18、小ストレート18、
フォーカインド24、大ストレート26、ヤッツィー40、チャンス0。
未成立の未使用役も選べ、ボーナスは0だが合計点は使う。使った役欄は消費する。

低い目を揃えたときのボーナスは高い目と同じ。たとえば1・1・1・1・6のフォーカインドは34点、
6・6・5・4・2のペアは27点となる。目の大小も役も寄与するが、高い目だけを待つ設計へ戻す意図はない。
保守的な停止や高い目だけを残す方針がどの程度強いかは、新仕様の実測で確かめる。
§8の900試合や旧固定得点の数値を、新仕様の証拠として流用しない。

通常の被害は低い側だけ10＋点差、同点は双方10。HP80から、どちらかが0になるまで続ける。
6ターン終了時の残HP判定を撤去し、役を9欄使い切った側だけ次ターンに全欄を戻す。
HPと保存の使用状態は戻さない。自動試合の安全上限16は総HP160と最低消耗10から導く内部の値で、
画面のターン上限や残HPで勝者を決める規則ではない。

### 9.3 保存は具体的な危険と次の手を交換する

「保存で今回の攻撃を0にし、同じ点を次ターンに移す」だけの案は採らない。
点数差の交換では現在の攻撃を捨てた分を回復できず、保存が有利になる理由が不足するためである。

採用した保存は人間側が対局中1回。現在の手の点数Pで敵へ攻撃し、敵の予告点数Nを全て受ける。
通常の相殺と基礎10は適用しない。双方の選択役を消費し、5個の目と保持状態を保存する。
生存して次ターンへ進むと、同じ目と保持状態を自動で復元し、さらに2回振り直せる。
保存によって使った役欄と保存の使用権を復元しない。9欄を使い切った場合の通常の更新は適用する。決着した場合は保存を失効させる。

P＝34、N＝27なら、通常は敵17・自分0の被害、保存は敵34・自分27の被害。
今回の全攻撃と被害を交換しながら、次の役を育てる初手を得る。抽象的な魔力ゲージを再導入せず、
保存ボタンに今回の与える被害・受ける被害と、次の2回の振り直しを表示する。
この交換がいつでも有利であるとは主張せず、HP・選べる役・現在の手に応じて判断する操作とする。

### 9.4 出目・入力・演出を一致させる

敵は人間の投擲前に手と役を固定する規則を維持し、その5個の実出目を開始時から小さいダイスで表示する。
開始時の投擲演出中に点数だけを先出しせず、出目・役・素点・ボーナスの根拠を揃える。
人間の操作を見て敵が手を変える処理は加えない。

クリックと横ドラッグで保持を選び、右クリックで振り直す。上へ92 Canvas単位以上弾いて離すと、
現在選択している役で5個全体を投げて確定する。届かなければキャンセルし、保持を元に戻す。
右側の役一覧はクリックに加えてホイールで選択できる。使用済みの役を飛ばして未使用の役だけを循環し、
モーダル表示中と振り直し中はホイールによる切り替えを無効にする。
ボタンとキーボードの代替操作を維持し、同じルール処理へつなぐ。モーダル中と投擲中の誤操作、
ドラッグ中の二重確定、閉じる入力の対戦への漏れを検証対象にする。

成立演出は役の種類と強さに対応させる。ペアの小さな集合、強い同目の集合、ストレートの連続、
フルハウスの3個と2個を異なる形で伝える。着地後にだけ通知し、目の回転演出中に結果を先出ししない。
動きを控えめにする設定でも、役と点数を伝える機能は維持する。

## 10. 役を倍率にする案の検討（2026-10-11、未採用）

ユーザーの「役はスコアの倍率にしてはどうか」に対し、現行の加算方式を正しい前提として扱わず比較した。
検討依頼であり、Coreの採点・NPC方針・HP・保存ダメージは変更していない。

倍率化には、役が揃っても残りのダイスを改善する意味が増す利点がある。同じ役なら出目合計の1点改善が倍率分の改善になる。
右の役一覧を倍率と最終得点、中央を「素点 × 倍率 ＝ 得点」にすれば、情報と操作を増やさず結果を伝えられる。
一方、同じ役の1揃いと6揃いの得点比は、単純な合計×倍率では常に1:6である。倍率の値だけではこの偏りを解消できない。
現行はヤッツィーの1揃い45点、6揃い70点。倍率化が自動的に低い目の価値や振り直しの面白さを改善するとは判断しない。

### 10.1 全出目と保持判断の試算

`scripts/Analyze-RoleMultipliers.py` で公正な5d6の7,776通りを、順序を除いた252状態へ確率を保ってまとめた。
全ての保持部分集合と残り最大2回の振り直しを列挙し、最終得点の期待値を最大化した。
結果は `logs/role-multiplier-study.json`。ペア1.2、ツーペア1.4、スリー1.7、フルハウス/小ストレート2、
フォー2.4、大ストレート2.5、ヤッツィー3.3、チャンス1の仮係数を比較用に用いた。未成立は倍率1。
係数は候補であり最適調整の結果ではない。端数処理を適用する前の計算で、実ゲームに小数得点を導入したものではない。

| 手 | 現行の合計＋ボーナス | 単純な合計×仮倍率 | （20＋合計）×同じ仮倍率 |
| --- | ---: | ---: | ---: |
| 1・1・1・1・1 / ヤッツィー | 45 | 16.5 | 82.5 |
| 6・6・6・6・6 / ヤッツィー | 70 | 99 | 165 |
| 1・1・2・2・2 / フルハウス | 26 | 16 | 56 |
| 1・2・3・4・5 / 大ストレート | 41 | 37.5 | 87.5 |

単純倍率では1のヤッツィー16.5点を崩して全て振り直すと、残り1回でも期待得点26.4566、2回なら35.4326となった。
現行加算では同じ手を5個全て残すのが最善45点。低いヤッツィーを完成しても捨てる方が有利になる候補は、
達成感と低い目の用途という要求に合いにくい。低い大ストレートでも1を振り直して高い側を狙う選択が最善になった。
ただし現行も低いフルハウス26点では、残り1回なら2の3個を残して29.9444点、2回なら全振り直しで33.5961点が最善だった。
既存加算も改善対象であり、採用し続ける根拠を「今そうなっているから」に置かない。

基礎20を加えた候補では低いヤッツィーと大ストレートを残す判断が最善になった。ヤッツィーの高低比も1:2へ縮む。
低いフルハウスでは2の3個を残して上位の役を狙う判断になり、全振り直しとの違いを作れる。
ただし得点帯が上がり、役を大きく評価しすぎる懸念もある。基礎20は候補であり確定値ではない。

この試算は全9役が未使用、相手・HP・保存・次ターンの欄価値を考慮しない期待得点だけの比較。
勝率、対局の最適戦略、人間の楽しさ、Steamでの販売実績の予測には使えない。

### 10.2 設計判断

倍率方式は試作する価値がある。ただし「出目合計に倍率を掛けるだけ」をそのまま本採用することは勧めない。
次の比較候補は **得点＝（基礎点＋出目合計）×役倍率** とし、基礎点で高低の幅を抑える。
ゲージや操作を追加せず、右側に倍率と現在の得点、中央に計算結果、相手に実ダイスと同じ計算を示す。
採用を判断する際は基礎点・倍率・端数処理を一緒に決め、NPC、HP、点差ダメージ、保存の全受けも再調整する。
全役未使用の期待値だけでなく、役が使われた対局、相手を上回った時の停止、低い役の保持、KOのテンポを比較する必要がある。
また、倍率に置き換えても「相手を上回れば通常の被害0」という勝負規則は変わらない。
安全な早止めが常に魅力的である問題を、得点式だけで解決したとは扱わない。公開された相手点数、残HP、
未使用役と振り直しの危険を含めて、上位の手を狙う具体的な利益が停止の利益と競合するか評価する。
単純な倍率表への置換、最低点の例外を多数追加する補修、倍率を上げるだけで達成感を説明する方針は採らない。

Hasbro公式Yahtzeeはフルハウス25、小ストレート30、大ストレート40、ヤッツィー50という固定得点と、
3/4カインド・チャンスの出目合計を使い分ける。低い目での役の達成を高い目の合計から独立させている点を参照した。
上記の基礎点＋倍率は本作の仮説で、公式ルールが裏付ける方式ではない。
一次資料：[Hasbro公式ルール](https://www.hasbro.com/common/instruct/yahtzee.pdf)。

## 11. ボタンを撤去し、下引きと離す操作へ変更（0.6.1）

ユーザーの入力修正を反映し、上へ弾く入力と「この結果を使う」「振り直す」の画面ボタンを撤去した。
代わりにボタン以外の卓全体から下へ引くと5個のダイスが追従して下がり、離すと選択中の役で相手へ発射する。

クリック・横ドラッグの保持、右の役のクリック・ホイール選択、右クリックの振り直しは維持する。

左の下向きガイドが移動し、3個保持時は右ボタンが光るマウス図形と右クリックの文へ切り替わる。

## 12. 基礎点と役倍率、共通軽減の同時ダメージを採用（0.7.0）

§10の試算を経て、得点を floor((20＋5ダイスの合計)×役倍率) に変更した。
ペア1.25、ツーペア1.5、スリーカインド1.75、フルハウスと小ストレート2、フォーカインドと大ストレート2.5、ヤッツィー3.25、チャンス1。未成立も倍率1で欄を消費する。倍率は1/4刻みで整数計算し、最後に切り捨てる。
基礎20により低い目の完成役にも価値を残し、同じ役の出目改善を倍率分だけ得点へ反映する。1のヤッツィー81点、6のヤッツィー162点。採用は人間の楽しさや販売品質を証明しない。

通常の点数をP、Nとし、共通軽減A＝floor(min(P,N)/2)を両方の攻撃から同じだけ引く。敵への被害P−A、自分への被害N−Aを同時に適用する。上回った側にも被害があり、低い側の攻撃も残る。双方HP240でKOまで続ける。各通常攻撃は最低13ダメージなので、自動試合の内部安全上限は19ターン。ターン数で勝者を決めない。
同時KOは、0に丸める前の残HPが多い側の勝ちで、等しい場合だけ引き分け。HP30/10、P56/N70なら残HP−12/−18で自分の勝ち。HP20/20なら−22/−8で相手の勝ち。今回の点数だけでなく、それまでのHP差も結果に残す。

保存は対局中1回の全攻撃交換を維持する。敵にP、自分にNの同時ダメージを与え、共通軽減は使わない。双方の役と保存権を消費する。生き残れば次ターンに同じ5ダイスと保持状態を復元し、さらに2回振り直せる。決着時は保存を失効させる。NPCの公正な実ダイス、予告の固定、独立乱数と役欄の更新周期は維持する。

画面は紺革の卓と右の羊皮紙役表を中心にし、KenneyのCC0 UI・Input Prompts・Game Iconsを使う。説明文は遊び方だけに置き、対戦画面は役名・数値・操作名・図形で伝える。保持は鍵、残り振り直しは点、右クリックはマウス図形で示す。§11の下引き・離す発射、クリックと横ドラッグの保持、役のクリックとホイール選択、キー代替を維持する。
§10と§11は当時の検討と入力変更の記録として保持する。現行仕様はGAME_DESIGN.mdを参照。0.7.0の最終検証証跡と確認範囲はTEST_REPORT.md §16に記録した。この設計記録は要求品質の達成を認定するものではない。

## 13. 標準の敵、実投擲の再生、直接入力と攻撃演出（0.8.0）

敵が役を揃えすぎるというプレイ報告を受け、従来の強いAIを「上級」（Expert）として残した。既定の「標準」（Balanced）は、見えている成立役・同目の組・4以上の目を保持して最大1回振り直す。上級と「上級・大役」（Aggressive）は従来の全出目を列挙する最大2回の期待値方針を使う。Carefulは内部互換用に保持し、難易度の画面には出さない。
出目の有利な選別や役の保証は加えない。独立した乱数列から初回5個と保持しなかったダイスだけを振り、人間の出目より先に確定する。初回・振り直しの出目と保持マスクを不変の履歴に記録し、各段階0.18秒で実際の経過を再生する。

実ScoreDuelの同じseed 0〜99で、保持方針patternの自動対戦は標準86勝/100、従来方針を残した上級47勝/100。4以上を残すhighFacesは標準59勝/100だった。一次記録は `logs/score-duel-benchmark-v08-20261011-151140.json`。限定した自動方針の比較であり、人間の勝率・楽しさ・最適戦略を示す値ではない。得点式、HP240、共通軽減と同時KO、保存、役欄の周期は§12のまま。

次へボタンを撤去し、攻撃終了後の背景・ダイス・無効領域など、ボタン以外のクリックで次ターンへ進める。早い押下、同じ入力の二重実行、モーダル中の入力を止め、モーダル中は演出も停止する。下引きガイドはマウスの押下と18px移動、42px移動する3段の山形へ変更し、ホイールは内側だけ上下4px動かす。攻撃終了後はクリック図形へ切り替える。
敵の5ダイスは中心(-144,211)、44px角・間隔51px。下の暗い予告プレート(-144,164)は縁だけに重ね、目を覆わない。

## 14. 持越を発射の選択へ統合し、卓と対称の役表を再構成（0.9.0）

旧「保存」は押すだけで即座にターンが進み、通常の下引き・発射と異なる操作だった。右の操作を「持越」の切替にし、選択時は5個の小ダイス、手を囲む括弧、軽減なしの被害予告を表示する。もう一度選べば解除できる。下引き・離す発射で初めて持越権を消費し、現在の攻撃と無防備な被弾を同時に解決する。次ターンに保存した5個と保持状態を戻す光跡を加えた。点数、役の消費、被害、2回の追加振り直しというコアルールは変えない。

相手の役を左、自分の選択役を右に並べることで、双方が同じ9欄を使うことを画面から読めるようにした。相手の現在の役は縦の印、消費済みは得点とチェックで示す。相手の予告は中央の役名→実際の5ダイス→小さな計算式→得点とし、暗い情報ウィンドウを外した。

左右の役表で中央の卓を押し縮めないよう、卓を画面幅の大部分へ広げ、半透明の役表をその上へ重ねた。自分のダイスを再び112pxにし、HP文字は上下ともバーの中央に揃えた。卓面と左右の情報に視覚的な接続を持たせつつ、中央の操作領域を確保する意図である。自動検査と実画面の確認範囲はTEST_REPORT.md §18に記録する。

ウェブ版ではOSの日本語フォントを前提にできないため、Noto Sans JPを同梱した。大きな点数は同フォントの行領域が表示枠を超えるので、数値欄だけ文字の切り捨てを解除した。下引きの案内は終点から上に戻る動きが逆方向の操作に見えるため、下げ切った位置でフェードアウトし、元の位置で再表示する循環にした。音源内に二度目の転がりが含まれるダイス音は、初回の転がりだけを残す。

## 15. 卓上の情報密度と持越の重みを調整（0.9.1）

## 16. 案2の構図と役一覧の可読性を採用（0.9.2）

## 17. 数字の可読性・持越の合図・敵体力の難易度（2026-10-15）

役表の3ケタ表示に続き、卓の数字を読む負担を下げた。得点はAoboshi Oneのまま58pxへ、相手の得点は50pxへ上げ、金色を明るい金（`SDScoreGold`）へ寄せて暗い縁取りを付けた。与ダメージと被ダメージは26pxの太字にし、与ダメージは金色、被ダメージは赤で固定して、同じ「−N」でも攻撃の向きが色で分かるようにした。HPが減る間は、そのバーの横に減少量を「−N」として出し、バーの伸縮と数字を同時に読めるようにする。残り振り直しの点は14pxへ広げ、暗い縁取りを付け、使い切った側も半透明で残して2枠あることが分かるようにした。

対戦画面の右役表で、使用済みの役名と点数は `SDRailUsed`（暗い青緑）に統一し、使える役との差を明度で示す。役を選ぶ画面でも同じ色を使う。

持越は押した瞬間に、中央の操作から金色の輪が広がる合図（342ms）を出す。解除時は灰色の輪で戻す。設定「成立時の動き：控えめ」では合図を出さず、状態色だけを切り替える。既存の「次ターンへ出目が戻る」演出とは別の、選択の合図である。

難易度「上級・高耐久」を追加した。判断は上級（Expert）と同じで、敵の初期体力だけを `ScoreDuel.EnhancedStartingHp = 360`（プレイヤーは従来どおり240）にする。乱数は同じで、HPプールだけが変わる。Coreの `ScoreDuel` コンストラクタに敵体力を渡し、`NpcMaxHp` を通じてHP表示・バー・予測の基準にする。タイトルの相手ボタンは4つに増やし、上級と同じ厳密判断のまま長期戦になる選択肢として示す。

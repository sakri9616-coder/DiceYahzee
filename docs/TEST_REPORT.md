### 3.4 模擬的欠陥の個別検証

**① 攻撃偏重（attack-heavy dominance）— 修正で緩和、未解消**
`Aggressive` の `mostUsedAttackShare` は baseline 0.9988 → cycle3 0.8061。攻撃個数ヒストグラム（1/2/3/4 個）は `Aggressive vs Aggressive` で baseline `[1,0,0,834]` → cycle3 `[45,140,13,823]`。5個全攻撃の比率は 99.9% → 80.6% に低下し、少数攻撃の選択肢が現実的に発生している。ただし 5 個攻撃が依然として最多である点は否定せず、残存課題として記録する。

**② 合理的な防御の発生 — 修正で解消**
`Aggressive vs Aggressive` の守護個数ヒストグラムは `[834,0,0,1]`（守護1個しか選ばない）→ `[823,13,140,45]`。守護3〜4個の割合が 0.1% → **18.1%** に上昇し、「相手の高攻撃を見越して厚く守る」手が統計的に現れ始めた。

**③ Guardian 型の脆弱さ — 修正で解消**
`Guardian vs Guardian` の制限時間到達率 1.0000 → 0.3340、引き分け 84/500 → 17/500、平均ラウンド 12.00 → 8.05、与ダメージ 2.47 → 17.49。「ほぼ殴らない守護同士が膠着する」事象は構造上解消した。

**④ 構造的膠着 — 修正で解消**
全体の制限時間到達率 0.2633 → **0.0707**、`timeLimitDraws`（Guardian vs Guardian）84 → 17。10 ラウンド上限に到達する試合は 4 件中 1 件弱まで減った。

**⑤ 時間・テンポの悪化がないこと — 満足**
平均ラウンド数 5.42 → **4.65**（短縮）。引き分け率低下と同時に試合長も短くなっており、「引き分けを減らすために試合を長引かせた」修正ではないことを示す。

### 4.3 検証中に発見し修正した不具合

1. **ルールパネルのボタン重なり**: 本文の最終行が「閉じる」ボタンに隠れる。パネル 950×680・本文 17px/870×560・ボタン (0,−305)/220×50 に再配置して解消（`21-rules.png` で確認。**この寸法は v1 時点のもの**で、v3 では変わっている。第10節の `logs/unity-rules.png` が現行）。
2. **ダイスの当たり判定**: リング画像をダイス本体と同じ GameObject に置いたため rect が canvas 全体に引き伸ばされ、5個のダイスが重なって `Die4` しか押せなかった。リングを子 GameObject に移し、無効ダイスではリング側の `raycastTarget` も落とすよう修正。修正後は実クリックで **Die0〜Die4 の5/5 が個別に応答**した。

以下は Step 5 の独立批評（`STEP5_REVIEW.md`）を受けて行った改修で、いずれも**ルール実装には触れていない**（そのため第2節の41テストは無変更で合格している）。

3. **効果音の尺が長すぎる（批評 U1・U2）**: 生成音は 1.6〜6.6 秒で、クリック音にも数秒の無音尾が付いていた。読み込み時に無音区間を自動トリムし、RMS を目標値へ正規化する処理を `GameAudio.PrepareSfx` に追加。実測のトリム結果: `die_keep` 6.14→**0.38秒**、`ui_click` 4.30→**0.28**、`hit` 6.14→**0.43**、`guard` 6.14→**0.68**、`commit` 5.18→**3.28**（第2回批評で**2.00秒の上限**を追加）。ゲインは `0.9/peak` で上限を打ち、**クリップ率は全10種で 0.00%**。
4. **違法な分割が押してからしか分からない（批評 U4）**: 「確定する」を分割が無効な間は無効化し、理由のヒントを常時出すよう変更。実機で全5個を守護にしたところ、`commit=False` ＋「攻撃と守護に、それぞれ1個以上のダイスを分けてください。」が**押す前から**表示されることを確認（`31-illegal-blocked.png`）。
5. **攻守が色だけの区別（批評 U3）**: 各ダイスに「攻」「守」のテキストバッジを追加。実機で 5個すべて守護のときに「守」が5個並ぶことを確認（`31-illegal-blocked.png`）。
6. **対戦相手が主ボタンに出ない（批評 U6）**: 開始ボタンの文言を選択中の相手名を含む形に変更。実機で「**守護型と決闘を始める**」と表示されることを確認。
7. **押し返しが初見で伝わらない（批評 D2・D5）**: ルール本文に具体例を追加し、表示崩れがないことを `32-rules-example.png` で確認。

以下は第2回の批評（`STEP5_REVIEW.md`「第2回批評」節）を受けた改修。

8. **BGM ループ境界に500msの無音空き（批評 R2-2）**: 数値解析の結果、素材の先頭に0.50秒の完全な無音があり、末尾は有効エネルギー（RMS 0.169）のまま終わっていた＝**毎9.17秒、0.5秒間 BGM が止まる**構造だった。`GameAudio.PrepareBgm` を追加して先頭無音を0.05秒に詰め、末尾100msをフェードアウト。加工後の実測は **head RMS 0.000→0.010、tail RMS 0.169→0.092、尺 9.17→8.67秒**、Play Mode で `bgm_duel_loop` が再生されることを確認。
9. **`commit` の3.28秒は長い（批評 R2-3）**: `MaxDuration`（`commit` 2.00秒、`ui_click`/`die_keep` 1.00秒）を追加し、トリムした全クリップの末尾に60msのフェードを付けて切り口を消した。読み込み後の実測で `commit=2.00` を確認。
10. **シード源が時計カウンタ（批評 R2-1 の前提部分）**: `StartMatch` のシードを `Environment.TickCount` から `Guid.NewGuid().GetHashCode()` 由来に変更。同ティックでの連続開始でも相関しない。ルール実装に触れていないため41テストは無変更（第2.1節の再実行で確認）。

以下は music API の本番 BGM を差し替えた際に、検証で発見して修正した2件。

11. **末尾無音のトリムが「件数」と「インデックス」を取り違えていた**: `PrepareBgm` に追加した末尾無音のトリムで、無音区間の開始インデックスをそのまま切り出し長さとして使っていたため、125.02秒の素材が **1.80秒** に潰れた（検証中にクリップ長が予想値と一致しなかったことで発見）。`total - (tailSilent + keepSilence)` に修正し、**121.82秒** になった。
12. **`Resources.UnloadAsset` を使うと BGM が途中で止まる**: トリム後のクリップを割り当てた直後に元素材を `Resources.UnloadAsset` で解放する最適化を入れたところ、対戦開始のクリック後に BGM の `isPlaying` が **False**（`time=28.8` で停止、以後 `Play()` でも再開しない）となった。メモリ節約よりも再生の確実性を優先し、この解放を撤回した。

### 4.4 実機で確認した挙動（要件との対応）

- 違法な確定が拒否され、ヒントが出て、ラウンドが進まないことを確認（要件「適法/違法操作」）

### 10.2 写真という検証手段

それまでの画面検証は**座標と文字列だけ**を読んでいた。
座標が正しく、ラベルが正しく、重なっていない — そのすべてが成立したまま
**形が正しくない画面**は作れてしまう。実際、完成を宣言できる状態で
ダイスは正円、ボタンは楕円として描かれていた。

`Assets/Tests/PlayMode/ScreenCaptureTests.cs` が PlayMode の実画面を
カメラ → `RenderTexture` → PNG に書き出し、`logs/unity-*.png` に出力する。
バッチ実行の Game view は **640×480（4:3）**で撮られるため、
「16:9 しか試していない」という従来の弱点も同じ写真で検査できる。

判定は次の3段で行った。

1. 写真を比較対象の基準画像と突き合わせる（`logs/ref-ywb-1..4.png`、Yahtzee With Buddies の公式画像）
2. 疑わしい箇所をスキャンラインに分解して `/`・`o`・`r`・`b` の記号列にし、形を座標で読む
3. 原因を特定したら、その形そのものを検証するテストを書く（§10.3）

写真は `logs/screens.html` に整形して見ることもできるが、
**この HTML は図形を四角で描くため形の判定には使わない**（判定は必ず PNG 側で行う）。

### 10.3 写真が見つけた不具合（3件、いずれも修正済み）

**① ダイスが正円、ボタンが楕円だった**

バッチ実行の写真 `logs/unity-title.png` で、役選択ボタン・開始ボタン・
ルール確認ボタンがすべて楕円として写っていた。数値で測ると、
横250単位のボタンの角半径が125単位（＝幅の半分）であり、これは角丸ではなく
**楕円そのもの**である。

原因は `Image.Type.Sliced` だった。九スライスは border を**スプライト寸法ではなく
載せ先の矩形に比例**させて算出するため、64px・border16 のスプライトは
「載せ先の半分」の角しか作れない。これが何の検証にもかかっていなかったのは、
それまで**スプライトの形を一度も見ていなかった**からである。

切り分けの撮影が `logs/unity-probe.png`。寸法を固定した320×120のImage一枚を
写すと、完全な楕円が写った。ここで「九スライスの問題」と確定できた。

修正は `UiFactory.RoundedSprite(int, int)` に**ウィジェット寸法そのものの
スプライトを生成し、`Image.Type.Simple`（既定）で表示する**方式への変更。
纹理のアスペクトが矩形と一致する限り拡縮は起きず、角は常に16単位になる。
大きいウィジェット（ルールパネル 820×700）は上限512pxで縮小生成するが、
**アスペクトを保ったまま**縮めるので角は歪まない。
同じ寸法はキャッシュして再生成しない。

回帰は `SpriteSkinTests`（角が切れている／辺が平ら／アスペクト一致／キャッシュ）と
`DiceShapeTests`（実画面のダイスが掴むスプライトが矩形の大きさと1対1で一致、
型が Simple、border が無い）が担う。

**② 4:3 で画面が切れ、ルールボタンごと画面外に出ていた**

同じ写真で、ブランド名・両者の名前・HPバーが左端と右端から切れており、
**`ルール` ボタンは完全に画面外**だった。

原因は `GameFlow.cs` の `scaler.matchWidthOrHeight = 1f`（高さ基準）。
640×480 の窓ではキャンバス横が960単位しかなく、1280単位分の内容が収まらない。

`CanvasScaler.ScreenMatchMode.Expand` に変更した。キャンバスが伸びるだけで
1280×720 の設計はいつでも内側に入り、余白はレターボックス側に回る。
再撮影で `ルール` ボタンを含む全要素が写っていることを確認した。
§9.6 の「アスペクト比別の見え方を見ていない」は、これで写真ベースに置き換わった。

**③ 攻/守バッジがダイスの輪郭に食い込んでいた**

バッジの縦位置が `-0.4 × サイズ` で、字の下端がダイスの端から1単位しか離れておらず、
ダイスが傷ついているように見えた。`-0.34` へ移し、ビーズ列の下に収めた。

### 10.4 写真を見直して行った改善

写真そのものが不具合ではないが、基準ゲームと並べて批評して手を入れた点。

| 変更 | 狙い | 根拠 |
| --- | --- | --- |
| ダイスに影を追加 | 正円時代の面のフラットさから「テーブルの上の物体」へ | `ref-ywb-1.png` のダイスは影と立体がある |

| 役の表示名をヤッツィー標準へ | 独自用語はプレイヤーの知識を無効にする | `GAME_DESIGN.md` §2.3 |

`ReadabilityTests` が、有効時・無効時の両方でラベルと地色のコントラストを

この種の欠陥は座標検証では絶対に出てこない。

## 24. HPバーの被害表記を1行へ統合（0.10.0 / 2026-10-17）

「被ダメージの表記方法が汚い」「強引な文字拡大で解像度が落ちている」という指摘を受け、各バーの被害を `あなた 350/350 −50` の1行（−50は赤）へ統合した。

従来は1本のバーに文字が2組あった。中央のHP文字（18px・`MiddleCenter`）と、右端の被害数字（26px・太字・`effectDistance(2,−2)` の濃い縁取り）である。被害は予測用（`_sdNpcDamage`／`_sdPlayerDamage`）と実減少用（`_sdNpcHpDelta`／`_sdPlayerHpDelta`）で別々のオブジェクトを持ち、同じバー内の右端x=222に重ねていた。拡大と太字は、排水中にクリーム色へ変わる帯の上でも数字を読ませるための措置だったが、結果として文字と縁取りが二重になり、拡大で輪郭が崩れていた。`logs/player-balance-20261017/smoke/hp-damage.png` でも、被ダメージの数字がクリーム色の減少帯と同系色の上に濃い縁取りだけで立っていた。

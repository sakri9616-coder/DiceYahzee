**3系統とも同じ4点に収束した。**

### 2.1 攻守分割は「攻撃合計という1本のスカラー」に潰れている（構造的事実）

自攻撃 `a`、自合計 `Tm`、相手攻撃 `A`、相手合計 `To`、`S = a + A` とすると

```
与ダメージ = max(0, S − To)      被ダメージ = max(0, S − Tm)
net        = max(0, S − To) − max(0, S − Tm)
```

- `Scoring.SumMask` は合計しか返さず、`CommitSplit` も攻撃合計と `myTotal − a` しか使わない。
- **攻撃側に入るダイスの「構成」はゲーム内価値に一切現れない。** 同じ攻撃合計なら30通りは完全に等価。
- `net` の傾きは区分線形で、攻撃を増やす価値があるのは `To < S ≤ Tm` の一箇所だけ。`S > max` ではフラット。
- 押し勝ちは**合計だけで**決まり、分割には依存しない。

→ 「どのダイスを攻撃にするか」は「攻撃合計をどこに置くか」の言い換えにすぎない。

### 2.2 相手の情報が全部非公開で、「読み合い」が成立していない

- 振り直し段階で NPC は `?` 5枚。合計も、既定の攻守予想も画面にない。
- `NpcBrain` は `TypicalOpponentAttack` / `TypicalOpponentTotal` の**固定値**で判断し、プレイヤーの手を見ない。
- ルール本文のコツ「相手の型に応じて攻守を切り替えます」は、判断材料が無いため実行できない。

### 2.3 操作フローがプレイヤーの意図を破壊している

- `EnterSplitMode()` は必ず `ResetSplitToDefault()` を呼ぶ → **振り直すたびに手動の分割が「上位2個」にリセットされる。**
- `DoReroll()` は `SetKept(new bool[5])` で保持も消える。
- さらに `PlayerKept` は**全 false 初期化**なので、何もクリックせず「振り直す」を押すと**手の5個すべてを確認なしで捨てられる**（今回の指摘。3系統とも未指摘の独立発見）。
- 「攻守を決める」→「振り直しに戻る」の往復は、分割を見ないと振り直しの良し悪しを判断できない設計から来ている。

### 2.4 結果の内訳が無い

- バナーは「あなた X ダメージ ／ NPC Y ダメージ」のみ。`攻11 − 守6 = 5` の内訳が無い。
- 押し勝ちも「（押し勝ち）」とだけ出て、合計の比較が出ない。
- ダメージ数値のフライ・アップ、画面効果、ダイス演出は一切ない。
- 下部ヒントは全フェーズで固定文で、ダイスをクリックできない状態でも「ダイスをクリックして保持」が表示される。

## 4. MiMo の判定

> **「現行 ARCANE DUEL を遊ぶ理由は、標準ヤッツィーや Dice Throne と比べてどこにあるのか？」**

**説得力のある答えが出なかった。** 現行版の意思決定は「攻撃合計をどこに置くか」という1次元の賭けで、その材料（相手の手）は非公開、その表現は往復を含む複数クリック、その結果は自分で足し引きしないと分からない。

したがって **中心ルールを維持する必要はない**と判定する。ただし既存実装は壊さず、**ルール層を設定で新旧切替可能にしたまま**、比較できる形で差し替える。

### 4.1 新しい中心（v2）

> **「5ダイスで『陣形』を組み、その陣形を攻撃に組み込めるか、守りに裂くかを選ぶ。」**

**陣形（formation）** = 5ダイス全体から読み取れる目組み合わせ。**攻撃側にその構成のダイスを全部入れると成立**する。

| 陣形 | 成立条件 | 効果 | 攻撃に出す個数 |
| --- | --- | --- | --- |
| 三つ | 同じ目が3個 | 攻撃にその3個を含むと **+5** | 3 / 5 |
| 階段 | **4つの連続する目** | 攻撃にその4個を含むと **+5** | **4 / 5** |

- 効果は `max(0, 攻撃合計 − 相手守護)` の**外側に加算**する（貫通できなくても陣形は必ず意味を持つ）。
- 1手に成立しうる陣形は**最も高いもの1つだけ**（積み上げない）。5ダイスでは三つと4連続階段が同時に成立しない。
- **初期案は「対 / 三つ / 3連続階段（+2 / +5 / +4）」だったが、計測で捨てた。** 同じ目が2個あるのは10回に9回で、
  役ではなく恒常的な加算になる（成立率 0.73・ボーナスが全体ダメージの 0.39）。3連続階段でも 0.70・0.38 にとどまり、
  **4連続に変えて初めて 0.51・0.31** に収まった。加算分で試合が半分に短縮されたため HP は 20 → 32 に上げ、
  試合長を 4.20 ラウンド（旧 4.65）で維持した。候補8種の実測は `logs/formation-sweep.json`、採用値は §6.1。

なぜこれが各指摘に効くか:

- **役の欠如（指摘3）** → 陣形という役が存在し、成立すると必ず効く。
- **スカラー化（2.1）** → 「攻撃合計が同じでも、陣形のダイスが入っているかで価値が変わる」＝**構成が意味を持つ**。
- **振り直しに目標がない** → 振り直しは「あと1個で階段」「三つを崩すな」という**複数の並行目標**になる。
- **読み合いの不在（2.2）** → 相手の陣形も公開時に初めて見える。隠れた最大の脅威を読むゲームになる。

### 4.2 操作の統合（v2）

- **モードを廃止し、1画面に統合する。** 各ダイスは 3 状態を巡回する: **攻 / 守 / 振り直し**。
- 振り直しボタンは「振り直し」状態のダイスだけを振る（残りは保持）。**保持の既定値が「何も残さない」危険を解消**。
- 分割は**振り直しを跨いでも保持される**（`ResetSplitToDefault` は毎回呼ばない）。
- 「確定」は1クリック。**最低操作数は「確定」1回**になる。

### 4.3 情報表示

- 常時表示: 手の合計、**成立している陣形の名前と現在の効果値**、攻撃合計・守護合計、振り直し残数。
- 公開時: `攻 11 + 三つ 5 − 守 9 → 7` の**内訳を時間軸で順に見せる**（Balatro の知見を小規模に適用）。
- 押し勝ちも `合計 24 vs 21` と内訳を出す。

### 4.4 演出

- 公開 → 陣形発動（名前＋演出）→ ダメージが攻撃側から HP バーへ飛ぶ → HP が減る、の順で**1.2秒以内**。
- 長押し・クリックで**即時スキップ可能**。テンポを阻害しないことを条件にする。
- 陣形成立・大ダメージ・撃破に専用の効果音（StepFun の StepAudio で生成、プロンプトとライセンスを記録）。

**出荷設定で型の相性差が広がっている（第5回批評で指摘され、再計算で確認した）**

v2 の非ミラー組合せは `攻撃型 vs 守護型 = 0.6606 / 0.3394` と極端に分かれた。
v1 の同組合せは 0.5340 / 0.4660 だった。**これは公平性の欠陥ではなく型の個性だが、
「どのNPCと戦うか」が勝敗をかなり決めてしまう**ことになる。
ミラー3組（同型どうし）は 0.4940/0.5060、0.4990/0.5010、0.4980/0.5020 とほぼ五分で、
**対称性そのものは保たれている**。

**この計測で見つかった、設計ではなく検証の欠陥（重要）**

- スイープの初回実行で、**先手勝率が 0.719** という値が出た。既存のミラー検証は
  「同じ型どうしの勝率」を見るため**席順の偏りを検出できない**（同じ型ならどちらが勝っても同じ数字になる）。
- 原因は**両席の判断ロジックが別物**だったこと：NPC席は `NpcBrain.TakeTurn`、
  プレイヤー席は `MatchRunner.ApplyRerollPolicy`（素の閾値）で、**陣形オフのときだけ一致していた**。
  つまり **v1 の数値は偶然一致していた**のであり、陣形を入れた瞬間に両席は別のゲームをしていた。
- 修正：リロール方針を `NpcBrain.PlanReroll` に1つに共有し、
  **席バイアス（先手勝率 0.45〜0.55）を検証に追加**した。集計値は 0.4817（v1）→ **0.4840**（v2）。
- **教訓**: 勝率が均衡していたことは、両対戦相手が同じルールで動いている証拠にならない。
  席そのものを指標にする必要があった。

**第5回批評で発覚した、記載側の欠陥（こちらも重要）**

上表は一度、**スイープの候補別値を3000試合レポートの値であるかのように記載していた**。
具体的には「先手勝率 0.494〜0.532」「型別勝率帯 0.35〜0.65 を全組み合わせ通過」
「最多攻撃数 0.465〜0.810 → 0.390〜0.739」「陣形成立率 0.51」の4項目が誤りで、
- 0.494〜0.532 は `logs/formation-sweep.json` の**8候補それぞれの値**であって、
  出荷設定1つを3000試合で測った値ではない（正しくは **0.4840**）。
- 「全組み合わせが 0.35〜0.65 を通過」していたのは**ミラー3組のみ**。非ミラーは 0.3394〜0.6606。
- 最多攻撃数の帯も、陣形成立率も、レポートから再計算し直した。

誤りの原因は明確で、**2種類の計測（8候補のスイープ／1候補の3000試合）の数字を、
出典を明記しないまま同じ表に並べた**ことにある。
次回以降は**すべての数値に一次ファイル名を添える**こととする。


### 6.2 操作ログ実測（`logs/oplog-summary.json`、現行ビルド）

実物の `GameFlow` を操作ハンドラ経由で駆動し、`InputLog` が全入力を記録した。
**各ポリシー5試合・計20試合の平均**（`runsPerPolicy: 5`）。
1試合では試合長の偶然がそのまま入力数になってしまうため、平均と範囲の両方を取っている。
「旧」は `GameFlow.ConfigOverride` で旧ルール（HP20・陣形なし）に戻した列、
「出荷」は `GameConfig.ApplyShippedPatternLayer()`（HP32・三つ+5・4連続階段+5）の列。
